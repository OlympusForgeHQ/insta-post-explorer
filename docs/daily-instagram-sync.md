# Daily Instagram sync

The existing worker now contains a runnable Chromium collector using the unchanged
Insta Saved Sync extension 4.2.8. Automatic scheduling is not yet active in Coolify.
Implementation lives on `feat/daily-instagram-sync`; no feature publication or
production migration has occurred. Manual sync from the PC remains supported.

## Behavior

The command first opens its private persistent profile and checks for an Instagram
session cookie. This checks session presence, not whether Instagram still accepts
it. It then obtains a fresh run JWT through `POST /api/v1/sync/session`, starts the
existing extension, renews the lease and polls server status. Only a persisted
`COMPLETED` job counts as success. The raw automation key stays in Node; the browser
receives only the temporary run JWT.

A PostgreSQL transaction lock serializes admission and writes per owner. Automatic
and manual runs cannot overlap for that owner. An automatic run is admitted at
most three times per local day, and never again after one success that day. Manual
runs remain available afterwards. Failed or crashed attempts can retry; completed
posts are retained and the next run receives the known-post snapshot.

A lease lasts five minutes and is renewed every 30 seconds. A crashed collector
loses the lease; the next admission marks its job failed. Obsolete imports cannot
commit. Post, media identity and job counters commit in one transaction. R2 object
verification precedes the transaction; previously issued presigned uploads cannot
be revoked, but their obsolete post imports are rejected. Legacy jobs created
before this migration retain their original 24-hour activity window.

Manual renewals live in the library controller, independently of the administration
menu. Keep the library page open during manual sync. Closing the page, putting the
PC to sleep or prolonged browser suspension can expire the lease; relaunch after
reopening. Instagram's scheduled pauses keep renewals alive. Another active run
produces a clear conflict message. No extension reinstallation is required.

## Configuration

| Location | Setting | Value / purpose |
| --- | --- | --- |
| Web | `INSTAGRAM_AUTO_SYNC_ENABLED` | `0` initially; `1` for the approved pilot and activation |
| Web | `INSTAGRAM_AUTO_SYNC_KEY_SHA256` | SHA-256 hex digest of a dedicated key |
| Web | `INSTAGRAM_AUTO_SYNC_TIMEZONE` | `Europe/Brussels` |
| Web | `APP_OWNER_ID` | Existing explicit library owner |
| Web | `NEXT_PUBLIC_APP_URL` | `https://insta-explorer.hz.kalyros.dev` |
| Worker | `SYNC_APP_URL` | Same exact public origin |
| Worker secret | `INSTAGRAM_AUTO_SYNC_KEY` | Raw dedicated `ips_sync_` key |
| Worker | `SYNC_PROFILE_DIR` | `/var/lib/insta-sync/profile` |
| Worker | `SYNC_TIMEZONE`, `SYNC_HOUR` | `Europe/Brussels`, `4` |
| Worker | `SYNC_MAX_RUN_MS` | `10800000` (three hours, configurable downward) |

Generate the key from 32 random bytes encoded base64url, prefixed `ips_sync_`.
Store the raw key only in the worker's secret configuration and the digest only
in the web app. It must differ from the read API credential. Never pass secrets
as command-line arguments, paste them into task logs or commit them. No real keys
have been generated by the implementation. Preview uses its own key/profile and
`https://preview-insta-explorer.hz.kalyros.dev`.

Automatic JWTs expire after four hours; manual JWTs after 24 hours. Disabling the
flag or rotating/removing the digest revokes subsequent automatic requests,
including already-issued JWTs, once the web process receives the new configuration.
Manual authorization is independent. Production origins must be HTTPS. Only
`http://localhost:3000` is accepted for disposable nonproduction rehearsals.

## Deployment and first login

Use the existing `services/worker/Dockerfile` and existing Coolify worker resource.
The image includes bundled Chromium; its normal worker entrypoint and healthcheck
are unchanged. It does not create another worker deployment or public endpoint.

1. Publish the reviewed change through the repository's normal PR flow. Apply the
   additive migration `20260911120000_daily_sync_leases` before updating the web
   process. Keep automatic authorization disabled until the pilot is ready.
2. Rebuild the existing web and worker resources. Preserve their current PostgreSQL,
   R2 and normal worker settings. Add the settings above only to the relevant
   resource. Mount a private persistent volume at `/var/lib/insta-sync`, writable
   by the image's existing UID/GID `10001:10001`. The profile itself must be `0700`.
   Do not reuse a personal Chrome profile or share one between environments.
3. Establish an existing private interactive display for the operator, accessible
   to UID 10001 (`DISPLAY=:N` or SSH-forwarded `localhost:N`, with its authorized
   `XAUTHORITY`). The CLI supplies the browser login flow; it does not install an
   X server or a remote desktop service. Inside a container, display socket and
   authentication access must be explicitly supplied for that private session.
   Do not expose X11, VNC or Chromium debugging publicly.
4. Run `node services/worker/dist/sync/cli.js login` in the same image/profile as
   scheduled execution. Complete Instagram login/2FA in that private browser and
   close it. Run `node services/worker/dist/sync/cli.js check`; `login_present`
   confirms a session cookie is present. A real `run` is still required to prove
   Instagram accepts it. Never copy cookies out of the profile.
5. Enable the web capability and run `node services/worker/dist/sync/cli.js run`.
   Require exit 0 with `completed`, inspect the app's imported posts and check for
   an Instagram challenge. The first real pilot can upload/import actual saved
   posts. No synthetic test claims that this live-account step has passed.
6. Add a scheduled command on the **existing worker container**:

   ```text
   Cron: 0 * * * *
   Command: node /app/services/worker/dist/sync/cli.js scheduled
   ```

   The command skips before 04:00 Brussels time and provides hourly catch-up after
   that time. Server admission ensures at most one successful automatic sync per
   day. Allow the command its configured three-hour execution budget; don't wrap
   it in a shorter external timeout. Prevent overlapping invocations in the
   scheduler where available. A simultaneous CLI invocation using the same
   profile refuses the Chromium lock and leaves the ongoing collector untouched.
   Coolify executes scheduled commands inside running containers; a stopped
   container cannot run them. Verify execution logs after activation.

The Chromium extension mechanism uses Playwright's bundled Chromium and a
persistent context ([Playwright documentation](https://playwright.dev/docs/chrome-extensions)).
Scheduled command behavior is documented by
[Coolify](https://next.coolify.io/docs/core/automation/scheduled-tasks/overview).

## API and operational outcomes

The successful session response contains `jobId`, `token`, `apiBaseUrl`,
`knownExternalIds`, `knownPostCodes`, paired `knownPosts` (up to 10,000),
`expiresInSeconds` and `heartbeatIntervalSeconds`. Responses are private/no-store.
The dedicated key grants neither administrator access nor the read-only V1 API.

Run JWTs authorize heartbeat, status, media preparation, post import and completion.
Session admission returns 409 with `SYNC_IN_PROGRESS`, `SYNC_ALREADY_COMPLETED` or
`SYNC_DAILY_LIMIT`. The first two are benign worker skips; the daily limit is an
error. Missing login creates no job. Login/challenge, timeout, lost heartbeat,
invalid response and unconfirmed completion exit nonzero with fixed error codes.
A stale profile task is cleared only after new exclusive admission, preserving
Instagram cookies, archive and unrelated extension data. Locks are never removed
to override an active browser.

For a challenge, stop scheduled attempts, use the private `login` flow again, then
verify with a real run. For rollback, disable scheduling and automatic authorization,
close the dedicated browser and preserve successful imports. The additive columns
can remain if application code is reverted; no data deletion is necessary.

## Repeatable verification

Run standard app lint/typecheck/tests/build and worker tests/typecheck/build. DB
checks require a disposable migrated PostgreSQL 16 `TEST_DATABASE_URL`. Browser
checks require the matching Chromium cache and permission to start local processes:

```bash
node services/worker/scripts/sync-browser-smoke.mjs
node services/worker/scripts/sync-collector-smoke.mjs
TEST_DATABASE_URL=<disposable-loopback-database> node services/worker/scripts/sync-app-smoke.mjs
```

The first verifies profile isolation, messaging and stale-task recovery. The second
runs the actual collector and media transfer against local/fake services. The third
uses real Next.js and PostgreSQL, intercepting only an empty Instagram feed; it
proves signed-session integration, completion persistence and daily deduplication.
The last two require free port 3000. All profiles are temporary and removed; all
Instagram session data and service credentials are synthetic.
